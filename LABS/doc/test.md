# Test Strategy

[back](../README.md)

## Purpose

This document defines the test strategy for PQTR:LABS. Testing validates that each component performs its intended function with mathematically verifiable results.

## Philosophy

### Synthetic Test Data

Tests use **synthetic images** with known properties rather than photographs. This approach provides:

- **Deterministic results**: Known input values produce predictable outputs
- **Mathematical verification**: Output can be verified against expected calculations
- **No subjective judgment**: "Correct" is defined by math, not perception
- **Fast execution**: Small images, quick generation
- **No external dependencies**: No sample photos to manage

### Module-Specific Images

Each module has synthetic test images designed to verify its specific behavior:

| Module | Test Image | Properties | Verification |
|--------|-----------|------------|--------------|
| Exposure | `exposure_ramp.png` | Gray ramp 0.0→1.0 | Value × 2^EV |
| Exposure | `exposure_midgray.png` | 18% gray (0.18) | 0.18 × multiplier |
| White Balance | `white_balance_patches.png` | Grays + R/G/B/Y | Channel ratios shift |
| Tone Map | `tone_map_hdr_ramp.png` | HDR ramp 0.0→4.0 | Highlight compression |
| Tone Map | `tone_map_ev_patches.png` | Patches at EV 0-4 | Luminance mapping |
| General | `colorchecker_srgb.png` | 24-patch ColorChecker | Industry reference |
| General | `gradient_shadow.png` | 1%→10% gradient | Banding detection |

### Test Data Generation

Synthetic images are generated by `gen_test_images`:

```bash
make -f Makefile.test gen-test-data
```

Images are stored in `tmp/var/test/data/` and regenerated on each test run to ensure consistency.

## Module Testing

### Test Pattern

Each module test follows this pattern:

1. **Load synthetic image** (gamma-encoded PNG)
2. **Convert to linear** (inverse gamma 2.2)
3. **Apply module** with specific dial values
4. **Print statistics** (min, max, mean per channel)
5. **Convert to gamma** (gamma 2.2)
6. **Save output** for visual inspection

### Verification Method

Tests print before/after statistics that can be verified against expected values:

```
Before exposure:
  Linear RGB: min=0.180144 max=0.180144 mean=[0.180144,0.180144,0.180144]

After exposure (dial=0.75, +2 EV, ×4):
  Exposed: min=0.720577 max=0.720577 mean=[0.720577,0.720577,0.720577]
```

**Verification**: 0.180144 × 4 = 0.720576 ✓

### Coverage by Module

#### Exposure (1 dial)

| Test Case | Dial | EV | Multiplier | Expected Result |
|-----------|------|-----|------------|-----------------|
| Neutral | 0.5 | 0 | 1× | Values unchanged |
| Dark | 0.25 | -2 | 0.25× | Values ÷ 4 |
| Bright | 0.75 | +2 | 4× | Values × 4 |
| Very Dark | 0.0 | -4 | 0.0625× | Values ÷ 16 |
| Very Bright | 1.0 | +4 | 16× | Values × 16 (HDR) |

#### White Balance (2 dials)

| Test Case | Temp | Tint | Expected Result |
|-----------|------|------|-----------------|
| Neutral | 0.5 | 0.5 | Minimal change |
| Warm (3000K) | 0.25 | 0.5 | Blue ↑, Red ↓ |
| Cool (10000K) | 0.75 | 0.5 | Red ↑, Blue ↓ |
| Green tint | 0.5 | 0.25 | Green ↑ |
| Magenta tint | 0.5 | 0.75 | Green ↓, R/B ↑ |

#### Tone Map (2+ dials)

| Test Case | White Point | Contrast | Expected Result |
|-----------|-------------|----------|-----------------|
| Neutral | 1.0 | 1.0 | Linear pass-through |
| High contrast | 1.0 | 1.3 | Midtones darkened |
| Compressed | 0.8 | 1.0 | Highlights boosted |

## Design Decisions

### Why Synthetic Images?

**Problem**: Testing with photos requires subjective judgment of "correct" output.

**Solution**: Synthetic images with mathematically defined properties:
- Gray ramp: Every pixel has known linear value
- ColorChecker: Industry-standard reference colors
- HDR patches: Known EV values for tone mapping

### Why Not Unit Tests with Assertions?

**Problem**: Image processing results have floating-point precision variations.

**Solution**: Print statistics for human verification + visual output inspection:
- Statistics show actual vs expected values
- Output images allow visual sanity check
- Both deterministic AND human-verifiable

### Color Space Handling

All tests follow this color space flow:
1. **Input**: Gamma-encoded PNG (sRGB)
2. **Processing**: Linear RGB (CV_32FC3)
3. **Output**: Gamma-encoded PNG (sRGB)

Tests apply inverse gamma before module, gamma after module, matching the real pipeline.

## Maintenance

### Adding New Module Tests

1. Create synthetic test image in `gen_test_images.cpp`
2. Create test executable `test_<module>.cpp`
3. Add to `Makefile.test` (sources, targets, rules)
4. Document test cases in this file

### Updating Test Images

If module behavior changes, update expected values in this document and verify new statistics match new expectations.
